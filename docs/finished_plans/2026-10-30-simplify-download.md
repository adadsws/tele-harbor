# 简化下载流程

## 需求

- 一个 Chrome 页面，消息和附件按新到旧处理。
- 不暴露批次、入队、队列日志等内部状态；终端只报告群组、扫描、逐文件结果和汇总。
- 保留登录、群组菜单、目录归组、已有文件核对及扫描续跑。
- 2026-10-30 修订：先确认下一完整编组，再下载上一编组；扫描最多领先下载 1 个已确认编组，不设每轮消息条数上限。CMD 输出需整体优化，不仅增加分数。

## 样例

| 输入 | 预期行为 | 预期输出 |
|---|---|---|
| 最新消息有两个附件，较旧消息有一个附件 | 确认下一完整编组后处理前一编组 | 单页面顺序下载，简短结果提示 |
| 完整历史已记录，旧附件缺失 | 扫描到已记录边界后处理旧附件 | 无需重新滚动全历史 |
| `--limit 1` 截在多消息归组中 | 只下载最新一条，额外扫描或使用缓存确认归组边界 | 文件进入正确目录 |
| 已有同 ID 文件 | 核对并复用，必要时迁移目录 | 不覆盖、不重复下载 |
| 单个附件失败 | 报错后继续下一项 | 最终失败计数与退出码 |
| 最新消息先形成一组，历史仍有更旧消息 | 再确认下一完整编组后暂停扫描并下载上一组 | 下载事件早于扫描第三组 |
| 单页下载时跳到媒体消息 | 下载后恢复刚才的扫描边界 | 继续扫描更旧消息，不重复或遗漏 |
| 已确认编组 A，继续扫描并确认 B | B 确认后开始下载 A，B 最多等待一组 | 事件顺序为确认 A、确认 B、下载 A |
| 历史总编组数未知、当前编组有 10 个附件 | 不臆测历史总量，使用当前已确认数与准确附件数 | `编组 1/2（已确认）`、`附件 1/10` 等清晰提示 |
