## 已证实的事实

| 检查 | 实际结果 | 能支持的结论 |
| --- | --- | --- |
| 按消息重取文档和新引用 | 文档 ID、access hash、大小及 DC 一致；本轮第一次引用变化，后续仍正常返回文档 | 消息和文档元数据可取得，已实际重取引用 |

| 超过文件末尾的对齐偏移 | 返回 upload.file、0 字节 | 请求能够得到正常 EOF 响应；范围内数据读取与 EOF 的结果不同 |

| 故意使用空引用的输入负例 | 约 0.2 秒返回 400 FILE_REFERENCE_EMPTY | 参数验证能返回具体 400，没有把所有错误都转换成 UNKNOWN |
| 同会话、同 DC 邻件 | 正常返回 4,096 字节；原生 requestFilePart 同样可读 | 当前会话及该 DC 的文件读取总体可用 |
| 文件传输会话与普通客户端会话；默认连接与显式 HTTPS | 原件仍为 500，邻件仍可读 | 更换这两类会话和连接方式未改变原件故障 |
| 原生 requestFilePart 原件 | 12 秒内未完成；本次结束时关闭隔离上下文 | 不能把原生路径的等待当成原件成功，也不能冒称它返回了明确 500 |
| 原件 getFileHashes | 返回 420 FLOOD_WAIT；按指定间隔后的有界复查仍被限速；停止继续查询 | 原件的服务端哈希尚未取得，不把限速算作校验失败或存储丢失证据 |
| 邻件 getFileHashes | 返回 8 个哈希块，覆盖 1 MiB | 哈希接口可对邻件正常工作；不据此推断原件哈希 |

依据 [Telegram 的错误定义](https://core.telegram.org/api/errors)，500 属于服务端内部错误；文件下载参数及引用错误分别见 [文件接口](https://core.telegram.org/method/upload.getFile) 和 [分片约束](https://core.telegram.org/api/files)。测试的分片大小与偏移符合这些约束。

## 当前定位及边界

故障点已缩小到 Telegram 处理该原件范围内数据读取的路径：文档描述、引用校验、缩略图、EOF 和邻件可用，只有原件有效范围的字节持续失败。约五秒的等待与后端读取失败/等待相符，这一时间机制仍是推断。

仅凭 UNKNOWN 无法继续区分原件数据缺失、存储副本异常或其他后端读取故障；缺少 Telegram 的服务端日志，不能断言文件永久损坏、已被删除或找到了物理层根因。增加本地重试次数、改文件路径或把缩略图算作原件均不构成恢复。
