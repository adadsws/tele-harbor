# 网页原消息定位与插件核对

## 范围

用户在 Vivaldi 打开第二群，要求通过插件核对并修复不能定位原消息的问题。仍不读取正文、原始文件名、缩略图和媒体内容；不改正式下载、扫描记录和登录数据，不处理远端 Git。旧 500 原件恢复及正序编号的剩余条件继续在遗留索引中跟踪。

## 实施与验收

- [x] 插件发现 Telegram 标签页，并读取到目标相册四个成员及前后消息结构。此时目标已由用户打开，不能算代理跳转成功。
- [x] 核对上游及当前部署的 Web K 路由，不以“群号_消息号”定位。URL 统一使用 `message=<原始编号>`；原生定位仍用内部号。两处回退先卸载旧页面，再全新加载目标链接，保留目标群/消息气泡核对。
- [x] 修正后 185 项离线测试通过，包含真实 Chrome 运行的中性路由夹具：先复现同文档路由失效，再用产品冷加载入口恢复定位，并覆盖原始/内部 ID、错误输入和相册成员。夹具没有 Telegram 登录、正文或真实媒体，不等同于 Telegram 实测。
- [x] Vivaldi 插件实际验证：同页导航返回最新消息；原生定位可命中；先卸载再全新加载后，准确四成员相册进入视口。
- [x] 在 Vivaldi 重新获取原件及邻件引用做 4 KiB 字节对照，原件明确 500、邻件成功，不保存或展示媒体内容；原件恢复移交原件排障。
- [x] 补查完整目标日期元数据到日期边界：21 页、2077 条普通消息、1047 个视频，目标正数 979、倒数 69。之前局部记录的 627 不能用于全天正数。
- [x] 以真实 BAT 在独立副本做 D01 fast/exact 两个回归，各 10 文件、52553905 字节，大小/哈希及原数据保护通过。只复测受影响路径，前一版本的 42 组合不冒充本次全部重跑。

## 失败、纠正与有效证据

最初普通 DOM 读取成功，底层调用却触发默认 30 秒工具超时和会话重置，随后提示“Debugger unattached”。用户重连后读取恢复，点击又超时；改为单步执行，并将慢调用工具时限设为 60 秒，实际约 43 秒返回，底层调试及原生导航恢复。不能把这些中断全部归为用户未连接或浏览器故障。没有安装扩展、改变浏览器调试权限或关闭用户窗口。

此前只验证 URL 参数就生成目标气泡的夹具不充分：真实 Web K 中，同一标签页跳转后，路由探针记录到实际定位调用的消息号为 0，页面停在最新端；改用原始编号仍复现。临时探针只记录群号/消息号等元数据，读取后恢复原函数，冷加载后所有页面临时状态均消失。原生接口可直接命中目标，证明消息仍存在。先卸载旧页再加载目标 URL 后，同群四成员相册实际进入视口；据此补齐产品冷加载入口及有状态夹具，不把仅地址改变记为通过。内部编号不是同页丢参的完整根因，URL 改用原始号是明确接口边界。

在 Vivaldi 新会话取得新引用后，原件约 6.99 秒返回 500 UNKNOWN，邻件约 0.66 秒返回 4096 字节，媒体落盘 0。这是明确失败证据，不是原件恢复。仍不能确认服务端物理层原因。
